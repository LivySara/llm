# 👍 point

- db.query('... WHERE ID = ?', [id]) 用占位符
> 参数化查询，杜绝 SQL 注入（这是最重要的一条安全底线，很多初学者会写成字符串拼接）
- createPool 而不是 createConnection
> 池化（Pooling）：复用昂贵资源、控制并发上限
- 每个分支处理完 res.end() 后 return
> Early Return / 卫语句：避免"响应发出后还在往下执行"的经典 bug
- 用 new URL(req.url, base) 解析 pathname + searchParams
> 协议解析的标准化：不要手写 split('?')

# ❌ pointer

- 错误边界（Error Boundary）。 任何"外部输入"和"外部依赖"都必须被包在一个兜底的地方。异步代码尤其要确认：异常到底在不在 Promise 链上。
- 业务与 SQL 混写 -> 分层 / 关注点分离 / 依赖倒置 -> Controller → Service → Repository
- 参数直接进 SQL -> 不信任任何输入（防御式编程）-> 边界校验函数 requireId()
- 密码/端口硬编码 -> 配置外置（12-Factor）-> .env + config/index.js
- 异常让进程崩溃 -> 错误边界 / 失败 -> 顶层 try/catch + HttpError 区分"预期错误"与"真 bug"

# 设计小项目（用户、商品、订单）

## 问题

- 用户和订单是什么关系？
> 个人：订单里存储，用户下单的订单信息
> 官方：一个用户可以有多个订单，一个订单属于一个用户。
- 订单和商品是什么关系？
> 个人：订单关联商品信息
> 官方：一个订单可以有多个商品，一个商品也可以出现在很多订单里
- 如果用 MySQL，我会设计几张表
> 个人：用户表，订单表，商品表
> 官方：用户表，订单表，订单明细，商品表
- 为什么要拆表
> 个人：信息数据归类
> 官方：不同性质的数据分开管理，同时通过 ID 建立关系。
- 查询“某用户的所有订单”怎么查
> select user.name, order.code, order.name
> from user
> inner join order
> on user.id = order.userId
> where user.id = 1
- 如果订单直接塞进用户数据里，会有什么好处
> 个人：在查询某个用户的订单时，用userId索引，可快速检索出数据
> 官方：需要一起读取的数据，可以一次拿到
- 如果订单数量达到 100 万条，塞在用户里面有什么问题
> 个人：不知道
> 官方：一个用户的数据变得非常大，在查询某个用户最近10个订单，完全不需要全部读取
- “创建订单 + 扣库存”为什么需要事务？
> 用户下单后，实际上仓库里的商品是少了，但是商品表里库存未减少，导致数据不一致
